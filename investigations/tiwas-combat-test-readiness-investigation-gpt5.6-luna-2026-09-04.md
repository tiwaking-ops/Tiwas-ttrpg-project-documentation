# Tiwas TTRPG — Combat-Test Readiness Investigation

## Randomly Generated Characters vs Template Creatures

---

# 1. Executive Finding

## 1.1 Investigative question

This investigation asks:

> **What systems must Tiwas have in executable form before randomly generated Tiwas characters can be reliably combat-tested against Tiwas creature templates?**

The answer is broader than the existence of an attack roll.

A valid combat test requires an executable chain covering:

```text
Random Character Generation
        ↓
Derived Statistics / Skills
        ↓
Creature Template Instantiation
        ↓
Equipment / Tags / Conditions
        ↓
Combat Initiation
        ↓
Turn / Action Sequencing
        ↓
Attack Test
        ↓
Defense Test
        ↓
Quality / Contest Resolution
        ↓
Outcome Effect
        ↓
Location
        ↓
Wound / Injury
        ↓
Armor Interaction
        ↓
Conditions / Secondary Effects
        ↓
HP / Resource Changes
        ↓
Incapacitation / Death
        ↓
Recovery / Healing
        ↓
Combat Termination
        ↓
Recorded Test Result
```

The current Tiwas corpus has **most of the architectural primitives for this pipeline**, and several of them have already received designer rulings. However, several components remain incomplete at the **content, integration, and executable-procedure levels**.

The most important distinction is:

> **A subsystem having a ruling or architecture does not necessarily mean that the subsystem is sufficiently specified to conduct a repeatable combat experiment.**

# 3. Combat-Test Definition

## 3.1 Proposed test population

The proposed experiment has two independently generated populations:

### Player-character population

Each test character is generated using the Tiwas character-generation system:

- 24 attributes;
- each attribute generated by `1d100`;
- derived statistics calculated from those attributes;
- Tier-1 Skills calculated from their underlying attributes;
- additional Skills/Advanced Skills only where legitimately available.

The Core defines the underlying mathematics, but a complete repeatable character-generation procedure is itself an implementation requirement identified in the project material. The roadmap specifically distinguishes the mathematical Core from the need for an ordered character-generation procedure and derived-stat initialization.

### Creature population

Each creature is instantiated from a Tiwas creature template.

Current project rulings establish that creature/NPC authoring may:

- pre-author Tier-2 Skills;
- give creature signature attack Skills full-Cap veteran values;
- use Tiwas-derived statistics rather than importing GURPS statistics;
- use pre-authored creature capabilities;
- bind environmental Traits to scene Tags where applicable.

DEC-085 through DEC-088 establish the current working methodology for the BToV-derived creatures, including the rule-faithful GPT-5.6 Luna baseline, signature-attack conventions, pre-authored Tier-2 Skills, and environmental conditional Traits.

# 5. Core Systems Already Available

## 5.1 d100 Resolution

The fundamental resolution engine is not a blocker.

Canonical Tiwas uses:

```text
Roll = 1d100
Success iff Roll <= Skill
```

with the canonical 100-Fumble rule.

The natural roll also remains authoritative for:

- resource Cost;
- Overflow;
- Failure XP;
- Double qualification.

Therefore combat testing must **not introduce a separate combat roll engine**.

The Core Test Transaction remains the underlying resolution primitive.

---

## 5.2 Resource Expenditure

Every test consumes the natural roll.

For combat this means:

```text
Body Skill Test → Physical Energy
Mind Skill Test → MP
```

If:

```text
Roll > Remaining Resource
```

then:

```text
Overflow = Roll - Remaining Resource
```

and Overflow becomes direct HP damage.

The project has explicitly strengthened this with DEC-007.A: Overflow cannot be reduced, redirected, absorbed, or otherwise modified by Tags, Traits, Effects, Conditions, or subsystems.

This is important for combat testing because **attack cost and damage are not interchangeable concepts**.

The creature-combat working methodology explicitly records:

> attack roll = attacker resource cost, not target damage.

That distinction must remain intact.

# 6. Character Generation

## 6.1 Mathematical readiness

The mathematical Core is sufficient to generate the basic character state:

```text
24 Attributes
        ↓
Derived Statistics
        ↓
Tier-1 Skills
        ↓
Starting Skill Values
```

The canonical formulas are established.

### Attribute generation

Each of the 24 attributes:

```text
Attribute = 1d100
```

### Health

```text
HP = Σ all 12 Body Attributes
```

### Mental Points

```text
MP = Σ all 12 Mind Attributes
```

### Physical Energy

```text
Physical Energy = bep + bes + bee
```

### Speed

```text
Speed = bsp + bss + bse
```

### Movement Speed

```text
Movement Speed = floor((bsp + bss) / 15)
```

### Skill Cap

For a Tier-T Skill:

```text
Cap = floor((A1 + A2 + ... + AT) / T)
```

### Starting Skill

```text
Starting Skill = floor(Cap / 2)
```

These are not missing mechanics.

## 6.2 Remaining character-generation requirement

What remains is an **executable generation procedure**.

A combat experiment requires every random character to be generated identically.

Therefore the test apparatus needs an explicit procedure defining:

1. attribute generation order;
2. derived-stat calculation;
3. Skill creation;
4. resource initialization;
5. initial Conditions;
6. initial Tags;
7. starting equipment, if equipment is part of the experiment;
8. any allowed pre-existing Advanced Skills;
9. any other permitted starting state.

The underlying rules exist, but the **repeatable experiment-generation procedure is not the same thing as the mathematical rules**.

This is an implementation/test-harness requirement rather than evidence of a missing Core mechanic.

# 7. Creature Template System

## 7.1 This is the largest content-side requirement

S-12 is explicitly a **content-authoring track**, not a universal creature mechanic.

The project ruling establishes that creature/NPC content is to be developed as authored templates rather than treated as a new replacement resolution engine.

For combat testing, each creature template therefore needs executable values for at least:

| Field | Required |
|---|---:|
| Attributes | Yes |
| HP | Yes |
| MP, if applicable | Yes |
| Physical Energy, if applicable | Yes |
| Skills | Yes |
| Signature attack Skill(s) | Yes |
| Defense capability | Yes |
| Armor state, if applicable | Yes |
| Relevant Tags | Yes |
| Relevant Conditions | Yes |
| Location configuration | Yes if location combat is enabled |
| Wound capability | Yes if creature can inflict wounds |
| Special Traits | Yes where applicable |
| Environmental bindings | Yes where applicable |
| Starting resource state | Yes |
| Equipment | Yes where applicable |
| Combat behaviour procedure | Yes for controlled tests |

## 7.2 Signature Skill ruling

DEC-086 resolves an important creature-authoring issue:

> Creature signature attack Skills start at **full Cap**, rather than the normal `floor(Cap / 2)` starting value.

General non-signature Skills may use normal starting mathematics or the permitted GM/content-authoring method.

This means creature templates can be deliberately authored as combat-capable entities without violating the PC Skill-generation model.

## 7.3 Pre-authored Tier-2 Skills

DEC-087 permits creature/NPC templates to contain pre-authored Tier-2 Skills.

This is important because Wound-capable creatures may require Tier-2 signature attacks without waiting for an in-play failed Double.

Thus:

```text
Creature Template
    ↓
Pre-authored Tier-2 Signature Skill
    ↓
Combat-capable creature
```

is currently permitted as content authoring.

# 8. Combat Resolution Pipeline

## 8.1 Attack

The attack must ultimately resolve through the existing Core Test Transaction.

No separate attack-roll system should be introduced.

Conceptually:

```text
Attacker
  ↓
Attack Skill Test
  ↓
Core Test Transaction
```

The test produces:

- Success/Failure;
- natural Roll;
- resource Cost;
- possible Overflow;
- Failure XP;
- possible failed Double;
- Recovery.

Only after that does the combat layer interpret the result.

---

# 9. Defense

## 9.1 Current status

S-6 Defense has received designer rulings.

The project explicitly records:

- Active Defense;
- post-hoc defense interaction;
- positive-Effect defense;
- repeated-defense fatigue;
- resource implications.

The earlier roadmap's broad dependency on S-6 therefore no longer represents an unresolved *decision*.

## 9.2 Remaining issue

The remaining problem is **integration**.

A combat test requires a fully executable sequence such as:

```text
Attack Test
    ↓
Attack succeeds?
    ↓
Eligible Effect
    ↓
Defense opportunity?
    ↓
Defense Test
    ↓
Defense succeeds?
    ↓
Effect prevented/mitigated?
    ↓
Otherwise Effect applies
```

The rules governing the components exist at varying levels of maturity, but the complete combat transaction must be implemented and tested as one pipeline.

This distinction explains why several earlier reports could simultaneously describe Defense as available while describing **Combat** as incomplete. The multi-LLM corpus contains precisely this distinction: individual foundations may be usable while full combat integration remains incomplete.

---

# 10. S-3 Outcome Effects

## 10.1 Architectural state

S-3 is structurally established.

The system uses Effects to convert successful tests into state changes.

The project has also ruled:

- one primary Effect per win;
- Quality as an Effect eligibility gate;
- no separate resolution engine;
- no natural-roll modification;
- no new resource pools;
- no ongoing DoT model.

The BToV Blood Man ruling is an example: Blood Seep is a **single-application Effect on a grapple win**, rather than imported GURPS-style continuous damage.

## 10.2 Combat-test requirement

For combat testing, every creature attack must have an explicit Effect definition.

For example:

```text
Signature Attack
    ↓
Successful Attack
    ↓
Eligible Effect
    ↓
Inflict Injury / Grappled / other defined Effect
```

The major remaining risk is therefore not the existence of S-3 but the **complete executable payload of every Effect used by the test creatures**.

# 11. Hit Location

## 11.1 Current status

The Tier-1 Location Index provider is established as **Zero-Step**.

It exchanges the tens and units digits of the natural d100 roll.

The original roll remains the authoritative Core roll.

This is therefore not a missing resolution mechanism.

## 11.2 Remaining requirement

For combat testing, the test must know:

```text
Location Index
    ↓
Anatomical Zone
    ↓
Wound / Armor / Effect interaction
```

The project has ruled the anatomical mapping framework, but the combat implementation must actually connect location results to downstream systems.

Thus:

**Location generation is available; complete combat consumption of location remains an integration requirement.**

# 12. Wounds and Injury

## 12.1 Critical combat dependency

This is one of the most important remaining areas.

The project has established the Wound structure and Quality × Skill-Tier ceiling.

However, the actual combat test requires concrete consequences from the resulting wound.

The distinction is:

```text
Damage / Injury
      ↓
Wound Tier
      ↓
Wound Magnitude
      ↓
Mechanical Consequence
```

The source material identifies wound-consequence implementation as a remaining development concern even after the fork-level OPEN-007 question was resolved structurally.

## 12.2 Why this matters

A creature combat test cannot be statistically meaningful if:

- attacks hit;
- HP decreases;

but the resulting injuries have no executable mechanical consequences.

Otherwise the test measures only **HP attrition**, not the Tiwas wound model.

---

# 13. Damage / Harm Magnitude

## 13.1 Major unresolved implementation area

The earlier BToV adaptation reports repeatedly identified a distinction between:

- having HP;
- having injury;
- and having a fully mapped damage/injury magnitude system.

One report explicitly characterised Tiwas as having HP and Overflow but lacking generally mapped damage amounts.

The current creature methodology likewise identifies **target-HP Inflict Injury magnitude** as an open item in the creature working baseline.

Therefore this remains a **critical combat-test dependency**.

## 13.2 Required executable relationship

A combat test needs a defined mapping of:

```text
Successful offensive Effect
        ↓
Inflict Injury
        ↓
Magnitude
        ↓
HP consequence
        ↓
Wound consequence
```

Without that mapping, the experiment cannot reliably answer:

> How dangerous is Creature X against Character Y?

# 14. Armor

## 14.1 Current state

S-5 has received substantial ruling.

Tags and equipment interaction are also structurally established.

The project specifically maintains the invariant that Armor does **not** modify Overflow.

## 14.2 Combat-test requirement

The experiment still requires concrete item instances:

```text
Weapon
├── relevant Tags
├── attack capability
└── damage/effect identity

Armor
├── relevant Tags
├── Location
└── applicable protection interaction
```

Therefore the missing piece is primarily **equipment content and combat integration**, not the basic architectural concept of Armor.

# 15. Equipment

## 15.1 Current ruling

DEC-081 establishes that equipment state is expressed through:

- Conditions;
- Tags;
- anatomical Location.

There is no independent equipment state tracker.

Held items automatically receive the Location of the holding limb.

## 15.2 Remaining combat-test requirement

The combat experiment nevertheless needs an actual equipment catalogue or test inventory.

At minimum:

| Equipment class | Required data |
|---|---|
| Weapon | Tags, attack Skill association, applicable Effects |
| Armor | Tags, Location, protection interaction |
| Shield | Tags, Location, defense interaction |
| Natural weapon | Creature-defined equivalent |
| Held item | Holding Location |
| Worn item | Worn Location |

The earlier adaptation reports correctly identified equipment as a major practical gap because combat cannot be meaningfully tested using only abstract attack Skills if weapon/armor interactions are part of the test.

DEC-079 now provides a substantial alpha Conditions vocabulary:

- Encumbered
- Grappled
- Restrained
- Prone
- Blinded
- Deafened
- Frightened
- Slowed
- Stunned
- Incapacitated
- Fatigued
- Sundered
- Poisoned
- Sickened

It also establishes the basic Condition format, magnitude relationship, production gate, stacking approach, and Body-skill scope.

## 16.2 Remaining requirement

For combat testing, the important issue is not deciding whether these Conditions exist.

It is ensuring that every Condition actually used by a creature has an executable:

```text
Application
+
Magnitude
+
Mechanical effect
+
Stacking
+
Duration
+
Removal
```

Therefore the Conditions system is **structurally available but still requires implementation/content completion for any Conditions actually exercised by the creature templates**.

# 17. Grappling

## 17.1 Critical because of creature design

Grappling is explicitly present in the alpha Conditions vocabulary.

It is also required by the Blood Man combat model.

The current Blood Man ruling specifies:

```text
Grapple win
    ↓
Blood Seep single-application Effect
```

rather than ongoing damage.

## 17.2 Remaining gap

The experiment needs a complete grapple interaction:

```text
Grapple attempt
    ↓
Contest / attack resolution
    ↓
Grappled Condition
    ↓
Defense / resistance interaction
    ↓
Subsequent consequences
    ↓
Release/removal
```

Earlier cross-model assessments explicitly identified Grappling as one of the areas where the broader combat system was incomplete.

Therefore Grappling should be treated as **required only for creatures whose templates actually use it**, but as a critical blocker for those creatures.

# 18. Time / Action Economy

## 18.1 Important correction to earlier gap assessments

Earlier adaptation reports often identified Time/Action Economy as a major missing system.

That status has since changed.

DEC-082 establishes:

> **Skill-side / Movement-penalty model only. No discrete action budget or action points.**

This is deliberately consistent with the Core's prohibition against creating another resource pool.

## 18.2 Remaining requirement

The combat test therefore does **not** require a conventional action-point system.

It does require an executable sequencing procedure:

```text
Combat State
    ↓
Who acts?
    ↓
What test is performed?
    ↓
When does the opposing participant defend?
    ↓
When are Conditions applied?
    ↓
When are resources recovered?
    ↓
When is the next participant resolved?
```

Thus the missing component is **combat sequencing**, not a new action economy mechanic.

# 19. Environmental / Conditional Creature Traits

DEC-088 establishes:

```text
Active only while [env:X] is present
```

as a Conditional-Trait Binding grammar.

`env:freezing` was added for the Ice Troll.

The Ice Troll's:

- Regeneration;
- Regrowth;
- DR

can therefore be bound to the freezing scene state.

## Remaining requirement

A combat harness must be capable of specifying:

```text
Scene Tags
    ↓
Trait activation
```

and recording those Tags as part of the experimental initial state.

This is especially important when comparing:

```text
Creature vs character in freezing environment
```

with:

```text
Creature vs character outside freezing environment.
```

# 20. Incapacitation and Death

## 20.1 Current state

The project has ruled:

```text
HP = 0
    ↓
Forced incapacitation
```

and related incapacitation/death procedures.

This is sufficient as a basic combat endpoint.

## 20.2 Creature-specific issue

NPC/creature behaviour after reaching a threshold is not universally supplied by the generic HP rule.

For example, the Ice Troll's source behaviour includes a Will-based decision at 0 HP.

The adaptation reports identified NPC morale/retreat behaviour as an area not covered by the basic player incapacitation rule.

Therefore a combat experiment needs an explicit **creature termination behaviour**:

| State | Required procedure |
|---|---|
| Creature alive | Continue |
| Creature incapacitated | Apply template rule |
| Creature dead | Remove from combat |
| Creature retreats | Remove from current engagement |
| Creature surrenders | End combat participation |
| Special threshold behaviour | Apply template-specific rule |

This is principally S-12 content/procedure.

# 21. Healing and Recovery

## 21.1 Single-combat test

Healing is not required if each combat is an isolated encounter and the experiment terminates immediately when one side wins.

## 21.2 Campaign-sequence test

Healing becomes mandatory if the experiment instead asks:

> How many randomly generated characters can survive a sequence of encounters?

Then the system must include:

- normal post-test Recovery;
- Rest;
- wound recovery;
- healing;
- persistent Conditions.

The project already has S-11 architecture/rulings, but it is unnecessary to include the complete healing loop in a single isolated combat unless the test specifically examines attrition across encounters.

# 22. Randomisation Infrastructure

This is a separate issue from game rules.

A scientifically useful combat experiment needs a deterministic randomisation procedure.

## 22.1 Required random inputs

At minimum:

```text
Character ID
Seed
24 attribute rolls
Combat initiative/ordering inputs, if any
Combat dice rolls
Creature selection
Creature parameter variation
Environment
Equipment selection
```

## 22.2 Required reproducibility

Every test should be reproducible from:

```text
Test ID
+
Random Seed
+
Character State
+
Creature State
+
Scene State
```

Without this, anomalous combat results cannot be reconstructed.

This is an **experimental infrastructure requirement**, not a Tiwas game mechanic.

# 24. Statistical Test Harness

## 24.1 One combat is not sufficient

A single random character against a single creature can demonstrate that the rules can execute.

It cannot establish:

- balance;
- lethality;
- resource sustainability;
- variance;
- creature consistency;
- Skill effectiveness;
- wound frequency;
- defensive effectiveness;
- or population-level behaviour.

For those questions, the test must use repeated trials.

## 24.2 Required population model

For example:

```text
N randomly generated characters
        ×
M creature templates
        ×
R repeated combats
```

The exact values of `N`, `M`, and `R` are experimental-design parameters and are **not established by this report**.

## 24.3 Required outputs

At minimum:

| Metric | Purpose |
|---|---|
| Character victory rate | Overall matchup |
| Creature victory rate | Overall matchup |
| Draw/undefined rate | Detect incomplete termination |
| Average combat length | Combat pacing |
| Median combat length | Outlier-resistant pacing |
| Average HP remaining | Survivability |
| Average resource remaining | Exertion |
| Overflow frequency | Resource-collapse behaviour |
| Wound frequency | Injury model |
| Wound severity distribution | Harm model |
| Condition frequency | Effect model |
| Defense success rate | Defense effectiveness |
| Attack success rate | Offensive effectiveness |
| Failed Double frequency | Progression interaction |
| Advanced Skill creation | Long-run advancement |
| Death/incapacitation rate | Lethality |

Again, these are **test metrics**, not proposed Tiwas rules.

# 25. Current Gap Classification

## 25.1 Critical blockers

The following should be treated as the highest-priority blockers to a **fully instrumented combat experiment**.

| Gap | Why critical |
|---|---|
| **Combat pipeline integration** | Individual subsystems must operate as one transaction chain |
| **Creature template completion** | A combat opponent must have complete executable state |
| **Inflict Injury magnitude** | Hit results must produce defined harm |
| **Wound consequence execution** | Injury must produce actual state consequences |
| **Creature-specific Effects** | Attacks need executable payloads |
| **Combat sequencing procedure** | Tests require deterministic ordering |
| **Combat termination procedure** | Test must know exactly when combat ends |
| **Test harness / logging** | Population testing requires reproducibility and traceability |

The Multi-LLM evidence independently identified Combat Integration, NPC/creature content, wound consequences, and incomplete Effect content among the principal remaining weaknesses.

# 31. Important Distinction: Rules Completeness vs Test Completeness

The central finding of this investigation is that the project currently has a substantial amount of **rules architecture and designer ruling**, but the threshold for a rigorous combat experiment is higher.

There are four distinct readiness levels:

| Level | Meaning |
|---|---|
| **L1 — Rule exists** | The mechanic has an authoritative/ruling-level definition |
| **L2 — Component executable** | The mechanic can be performed in isolation |
| **L3 — Pipeline executable** | The mechanic interoperates correctly with adjacent systems |
| **L4 — Experiment executable** | The complete system can be repeatedly tested and statistically analysed |

A system can therefore be:

```text
L1 = Yes
L2 = Yes
L3 = No
L4 = No
```

and still legitimately be described as **not ready for combat population testing**.

This explains the apparent tension in the existing adaptation reports: several reports found the individual foundations sufficient for playtesting while also identifying full combat integration as incomplete.

# 32. Final Investigative Conclusion

## 32.1 What Tiwas already has

Tiwas currently possesses the major foundational primitives required to construct the combat experiment:

- d100 roll-under resolution;
- 24-attribute character model;
- derived statistics;
- Skill mathematics;
- resource expenditure;
- Overflow;
- Failure XP;
- Advanced Skills;
- opposed contests;
- Location architecture;
- Outcome Effects architecture;
- Wound architecture;
- Armor architecture;
- Defense architecture;
- Incapacitation/death;
- Conditions vocabulary;
- Tags vocabulary;
- Equipment state model;
- Time/Action model;
- creature-authoring conventions;
- environment-conditional Trait binding.

The updated project state explicitly records these newer foundations and the closure of the previous fork-level OPEN items.

## 32.2 What is actually missing for the proposed experiment

The most important remaining requirements are:

### 1. **Complete executable creature templates**

The creature authoring track exists, but individual templates must be completed.

### 2. **Complete combat integration**

Attack → Defense → Effect → Location → Injury → Wound → HP/Condition must function as one pipeline.

### 3. **Concrete injury/harm magnitude execution**

A successful offensive Effect must produce a deterministic target consequence.

### 4. **Executable wound consequences**

Wounds must have operational consequences rather than merely existing as recorded states.

### 5. **Combat sequencing procedure**

The experiment needs a deterministic procedure for repeatedly resolving combat.

### 6. **Creature-specific combat behaviours**

Each template needs explicit behaviour where behaviour is necessary for reproducible testing.

### 7. **Equipment/item content**

Where weapons, armor, shields, or other equipment affect the matchup, the relevant concrete items must exist.

### 8. **Conditional systems**

Grappling, Conditions, environmental Traits, and special abilities must be completed for creatures that exercise them.

### 9. **Combat termination rules at the experiment layer**

The harness must distinguish victory, defeat, incapacitation, retreat, surrender, and other permitted termination states.

### 10. **Experimental harness**

Random character generation, creature selection, seeded randomness, full transaction logging, and statistical aggregation are required for a population-level combat study.

# 33. Overall Assessment

## Question

**Can Tiwas currently support the concept of randomly generated characters fighting Tiwas creatures?**

### Answer

**Yes, as a constrained alpha experiment; not yet as a fully instrumented, system-complete combat-validation programme.**

The Core is sufficiently mature to generate and resolve individual tests. The project now also has substantially more supporting combat architecture than existed when the original 25 LLM adaptation reports were produced.

However, the remaining bottleneck has shifted from **designing every major subsystem** to **finishing the executable integration and content layer**.

The highest-value immediate target is therefore not another broad combat-system redesign.

It is:

```text
COMPLETE CREATURE TEMPLATE
        +
COMPLETE COMBAT PIPELINE
        +
COMPLETE HARM/WOUND EXECUTION
        +
REPRODUCIBLE TEST HARN
```

Once those four components are operational, randomly generated character-versus-creature combat testing becomes a viable **systems-validation instrument**, rather than merely a manually adjudicated playtest.
