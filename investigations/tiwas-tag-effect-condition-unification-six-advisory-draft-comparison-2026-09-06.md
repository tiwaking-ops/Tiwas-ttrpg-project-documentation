## 1. Executive Summary

Six LLM advisory inputs responding to the same unification prompt (`Prompt - tag condition effect unification1.md`) have been stored in `investigations/` and recorded as a single non-ruling advisory-cache annotation on DEC-080. This report consolidates their findings into a side-by-side comparison across the seven decision axes on which the six documents substantively engage:

1. Executive verdict on the unification hypothesis.
2. Proposed record schema (the widest divergence).
3. "Tags counter Tags" mechanism.
4. "Tags and Conditions are NOT distinct" and the `Z = −Y` rule.
5. Tag removal.
6. Permanence encoding.
7. DEC-025 (Skill-Tag prohibition) risk posture.

The six inputs agree on the core proposition — one shared state-record shape with three fiction-level semantic Types, Tags stateless toward resource pools, no second resolution engine, DEC-007.A absolute — and diverge sharply on schema breadth, counter semantics, `Z = −Y`, removal rules, and DEC-025 risk. No input enjoys authority over any other; convergence between inputs confers no authority (see §8).

## 4. Comparative Analysis by Decision Axis

### 4.1 Executive Verdict

| Doc | Verdict |
|---|---|
| D1 | **Partial merge.** Merge Effect+Condition now; keep Tags on a compatible but mostly-inert schema. Reject literal Tag/Condition identity and a generic Tag-vs-Tag counter primitive. |
| D2 | **Adopt the architecture, not the identity claim.** One record + three semantic Types; reject literal semantic collapse. |
| D3 | **Conditionally adopt** minimal unification; collapse record format and production/removal surface; explicitly reject unrestricted Tag-vs-Tag counters that modify pools. |
| D4 | **Net-negative in full; strongly positive as a data-layer schema standard only.** Adopt record unification; reject dynamic tag countering and general tag removal. |
| D5 | Viable **if implemented minimally and structurally**; total complexity does not fall unless permanence, removal, and precedence are explicitly formalized. |
| D6 | Worthwhile **provided permanence and counter behaviours are derived meta-rules**; preserve no-resource-economy and single-resolution-engine constraints. |

### 4.2 Record Schema (widest divergence)

| Doc | Schema | Characterisation |
|---|---|---|
| D1 | Type, ID, Location(X) optional, Tier(Y) required for Effect/Condition and optional for Tag, Magnitude(Z, `Z = −Y` when present), Persistence (per-Type default, not stored per-instance unless overridden), Removal (required iff Persistent), Source | Mid-size; numeric fields optional/inert for ungraded Tags |
| D2 | **Smallest** — Type, Name, Tier Y, Magnitude Z, Location X. Explicitly: "No duration field", no resource fields | Fields optional/Type-defined; Type-lifecycle bears permanence |
| D3 | Type, Identity, Tier (integer Y ≥ 0), Magnitude (Z; default `Z = −Y` for Conditions), Location (optional), Source, **Duration enum {Permanent, Temporary, Named} + timer/trigger, StackRule enum {Replace, Add, Highest, Special}** | Prescriptive 8-field variant |
| D4 | ID, Type, **Subtype**, Tier Y, Magnitude Z, Location X (optional), **State Flags** {Read-Only, Persistent, Transient, Transactional} | Flags-based lifecycle; Tag `Z = 0`; Condition `Z = −Y` |
| D5 | Type, Tier (int ≥ 0), Magnitude (int), Location {None, Tier1, Tier2}, **Persistence {Permanent, Temporary, NamedDuration}, StackRule {Add, Replace, Highest, Special}**, Source | Prescriptive 7-field variant with 2-value Location |
| D6 | **Largest** — type, subtype, id, tier (int Y), magnitude (int Z), location, source, **duration enum {instant, scene, session, permanent} (optional, Type-default), removal_tags list, counters list** | Counter/removal as explicit queryable record fields |

Luna's D2 explicitly warns (§7.3) that universal persistence/counters/stacking/replacement/removal/promotion/Type-conversion fields turn the backbone into a "mini programming language". D3/D5/D6 add Duration+StackRule (or list) fields regardless.

### 4.3 "Tags counter Tags"

| Doc | Mechanism | Notes |
|---|---|---|
| D1 | **Compound boolean clause** on the consuming Trait/Effect (extends DEC-088's single-Tag Condition Clause): e.g. `Active only while [env:darkness present] AND [creature lacks tag:night_vision]`. **Reject** Magnitude-vs-Magnitude Tag arithmetic. | No Tag ever evaluates another Tag; countering lives in the consumer. |
| D2 | **Read-only relational predicate**: `Active(A, C) = Present(A) AND NOT Countered(B, A, C)`. Neither Tag is removed; suppression is per-consumer. | New canonical formulation offered: "Tags do not execute mechanics; they may be operands in mechanical predicates evaluated by consuming rules." |
| D3 | **Permission-precedence**: when conflicting Tags co-exist, higher Tier or more-specific Identity wins; the loser remains on the record but is ignored by permission checks. No roll, no resource, no Tag mutation. | If a counter requires roll/resource/state-change → violates the guardrail and must be rejected. |
| D4 | **Reject countering outright.** `env:darkness` is an S-1 roll-assembly permission gate; `trait:night-vision` *satisfies* the requirement — it "does not destroy or counter darkness". | Protection of DEC-080/REQ-017 read-only-ness is the stated reason. |
| D5 | Relational Tag counters override numeric fields (Precedence rule 2); cites DEC-059 ("Tag counters are relational predicates") among conflict sources. | Novel 5-rule Precedence Model (Condition > Effect > Tag; relational counters override numeric fields; Tier2 > Tier1; Permanent > Temporary; Special StackRule overrides all). |
| D6 | **Declarative `counters: list<text>` field**; id-match: "If a target has a StateRecord whose id is in another record's counters list, the countered record's effects do not apply." | Pure filter; no rolls or pools. |

D1, D2, D3, D5, and D6 converge in substance (read-only suppression, no second engine) with differing expression; D4 forbids even the counter relationship's language, re-expressing the same outcome as gate-satisfaction.

### 4.4 "Tags and Conditions are NOT distinct" + `Z = −Y`

| Doc | Tags/Conditions | `Z = −Y` |
|---|---|---|
| D1 | Reject literal identity; adopt **Type/Subtype** — a record may declare `Type: Tag` and carry a Condition-shaped body (generalised Sundered precedent). | Retained for Effect/Condition (DEC-035.A cl.3 / DEC-079 C2); inert for ungraded Tags. |
| D2 | Condition is a **semantic Type of the unified state-record system**, not a separate mechanical subsystem. | Retained for negative mechanical states; not imposed on descriptive Tags. |
| D3 | Mechanical distinction **discarded** (largest complexity win); fiction split carried by the Type field. Also supersedes Proposals §10/§11 wording. | Retained as Condition default under the unified schema. |
| D4 | **Rejected** — merging violates Proposals §11 and DEC-079's dedicated condition machinery. | Retained (DEC-079; Tag `Z = 0`). |
| D5 | Condition = the Type whose records carry Tier-Y / Value-Z = −Y, removal rules per identity. | Retained. |
| D6 | Formats merged into one `StateRecord`; **`Z = −Y` is ABOLISHED**, replaced by interpretation (Tier-based disadvantage tables). | **Abolished — the most aggressive departure from DEC-079 among all six.** |

### 4.5 Tag Removal

| Doc | Position |
|---|---|
| D1 | **Adopt generally.** Every `Persistence: Persistent` Tag must declare a Removal trigger (named action/Effect, or GM Fiat). No conflict — fills a genuine corpus gap. |
| D2 | Not a standalone mechanic; removal rides the **Type lifecycle**. Sundered becomes one record with a projected Tag identity — duplicate Tag+Condition records for one state are not retained. |
| D3 | **General removal**: (a) duration expiry, (b) named action/Effect defined as remover for that Identity, (c) explicit higher-Tier opposing Effect. |
| D4 | **Reject routine removal.** Tag modification requires explicit structural repair/healing/environmental mutation actions (S-4/S-5). |
| D5 | "Tags: … no removal except Sundered." |
| D6 | **Restrictive allowlist**: `removal_tags`; "An Effect can remove a StateRecord if the Effect's id is in that record's removal_tags." More restrictive than D1/D3 general removal. |

Three-way split: generalise (D1, D3) vs restrict (D4, D5, D6) vs lifecycle-only (D2).

### 4.6 Permanence Encoding

| Doc | Encoding |
|---|---|
| D1 | Per-Type **default** (Tag → Persistent, Effect/Condition → Temporary), overridable at authoring; Persistence not a stored per-instance axis; adds only a Removal field. |
| D2 | **Type-lifecycle behaviour only**; no persistence/duration field. |
| D3 | **Duration field** enum {Permanent, Temporary, Named} + optional timer/trigger + StackRule field. |
| D4 | **State Flags** {Read-Only, Persistent, Transient, Transactional}. |
| D5 | **Persistence field** {Permanent, Temporary, NamedDuration} + StackRule field. |
| D6 | **Duration field** enum {instant, scene, session, permanent}, optional, defaults by Type. |

### 4.7 DEC-025 (Skill-Tag Prohibition) Risk Posture

DEC-025 is a **non-canonical designer ruling** (register status: Ruled): Effects are granted by declared S-1 outcome; a formal tag/category system on Advanced Skills was rejected; no Skill-side tag data.

| Doc | Posture |
|---|---|
| D1 | **Not reopened.** State records live on characters/items/locations/scenes, not the Skill list; flags the risk of accidental re-litigation. |
| D2 | Conflict **HIGH if implemented incorrectly**; the unified architecture does not reopen DEC-025 by itself; tagging Skills would be a separate decision requiring explicit reopening. |
| D3 | **Not reopened.** Unified StateRecord does not touch the Skill system. |
| D4 | **Strongly threatens DEC-025.** With Tiers + counters on Tags, players will demand Skill-side tags to interact with the counter matrix. |
| D5 | Lists DEC-025 among identified conflicts; gating stays at trait/equipment/environment level. |
| D6 | Keeps gating at trait/equipment/environment; explicitly forbids Skills requiring Tags. |

5 of 6 keep DEC-025 closed; only D4 rates the unification itself as a high threat to it.

## 5. Convergence Findings

The following points are stated by all six advisory inputs (stated positions verified per doc above):

1. **One shared record shape**, differentiated by a Type field, with three fiction-level semantic Types (Tag, Effect, Condition).
2. **Tags remain stateless toward resources**: no HP/MP/Energy/XP/Overflow/pool modification; DEC-007.A and Invariant 17 are held absolute.
3. **No second resolution engine** (Invariant 18): counter interplay is consumer-side filtering or gate evaluation, never new rolls, pools, or a parallel engine.
4. **Fiction-level language preserved**: rules text continues speaking of "Tags", "Effects", "Conditions".
5. **Effect production stays S-1-gated** (DEC-023–030/DEC-107: winning S-1 produces the Effect; auto-apply per DEC-027).
6. **All six self-label non-canonical** and advisory; none claims authority; all are pending the designer's review.

## 6. Divergences Requiring Designer Ruling

1. **Schema breadth** — Luna-minimal (D2: 5 fields, no duration) vs Perplexity 9–10 fields (D6) with Duration/StackRule (D3, D5) or Flags (D4); D1 mid-size with inert-by-default numeric fields.
2. **Counter mechanism and vocabulary** — compound clause (D1) / relational predicate (D2) / permission-precedence (D3) / id-match list field (D6) / refusal of counter language with gates instead (D4) / 5-rule precedence model (D5).
3. **The `Z = −Y` rule** — retained by D1/D2/D3/D4/D5; **abolished by D6** (interpretation-based negative scaling).
4. **Tag removal scope** — general removal (D1, D3) vs allowlist-restricted (D6) vs repair/healing-only (D4) / no-removal-except-Sundered (D5) / lifecycle-only (D2).
5. **DEC-025 risk posture** — the other five see it as not reopened / high-only-if-misimplemented; D4 rates the unification itself as strongly threatening it.
6. **Adoption sequencing** — D1 suggests promoting the Effect+Condition half independently and ahead of the Tag half; D2 recommends a two-phase adoption boundary (architectural ruling first, selective collapse later); D3/D5/D6 present one-package proposals.

## 7. Cross-Cutting Observations

1. **Internal inconsistency in D6**: its Executive Summary says permanence and counter behaviours should be "derived meta-rules rather than new core fields", yet its own schema stores `duration`, `removal_tags`, and `counters` as record fields.
2. **Internal inconsistency in D5**: §2 asserts the report "does not introduce new mechanics", while §4.2 proposes a five-rule Precedence Model (which is itself a proposed mechanic).
3. **Factual error in D4**: §5 lists DEC-080 under "Preserves (Canonical/Locked)". DEC-080 is a **non-canonical designer ruling** per the decision register; the locked items are DEC-007.A, DEC-016 (Invariants 17–18), and REQ-017.
4. **DEC-059 usage varies**: D5 lists DEC-059 ("Tag counters are relational predicates") among *conflicts*; other inputs (D2, D4) treat DEC-059-adjacent relational/stateless consumption as *supportive precedent*. Both readings are represented in the corpus; the register defines DEC-059 as Bypass = a stateless relational Tag-pair property (neither Tag altered).
5. **Sundered is used as proof of opposite conclusions**: D1/D2 cite Sundered to justify Type/Subtype generalisation; D4/D5 cite it to justify restricting removal.
6. **D5 ends with an embedded offer** ("governance summary / promotion ready / side by side / ruling packet") that is part of the stored document's content. It was not acted upon as a directive.
